# SKUD

Проект сейчас состоит из двух частей:

- `create_google_sheet.py` — настройка Google Sheets со справочниками
- `docx_leadership_sync.py` — синхронизация шаблона связей руководства из Google Sheets в рабочие листы
- `app/` — backend-оболочка бота для MAX на `FastAPI`

## Структура

```text
skud/
  app/
    api/
    bot/
    integrations/
    schemas/
    services/
  create_google_sheet.py
  docx_leadership_sync.py
  .env
  data/
  requirements.txt
```

## Переменные окружения

Файл `.env`:

```env
MAX_BOT_TOKEN=
MAX_BOT_SECRET=
MAX_BOT_WEBHOOK_URL=
MAX_API_TIMEOUT_SECONDS=3
MAX_DELETE_PREVIOUS_MESSAGE=true
APP_HOST=127.0.0.1
APP_PORT=8000
APP_DEBUG=true
DATABASE_URL=sqlite:///./data/attendance_bot.db
GOOGLE_SERVICE_ACCOUNT_FILE=/Users/goocbk.ru/secure/attendance-max-bot-service-account.json
GOOGLE_SHEETS_SPREADSHEET_ID=1tg5umqy7-72LMLEaXu6n29OvGDSpkOE_adw_7PxsP54
GOOGLE_SHEETS_EMPLOYEE_RANGE=Сотрудники!A:R
GOOGLE_SHEETS_SCHEDULE_RANGE=Графики!A:X
GOOGLE_SHEETS_CACHE_TTL_SECONDS=300
OFFICE_SEAL_COMPANY_TIMEZONE=Europe/Amsterdam
OFFICE_SEAL_WINDOW_START=18:00
OFFICE_SEAL_WINDOW_END=22:00
OFFICE_SEAL_PHOTO_DIR=./data/office_seal_photos
PUBLIC_BASE_URL=
```

Роли из `Сотрудники` бот перечитывает через кэш и in-memory индекс, чтобы не упираться в лимит чтения Google Sheets на каждом webhook. Если Sheets временно недоступен, бот использует последнюю валидную копию. Кэш также защищает расписания: если `Графики` временно не читаются или упираются в лимит, импорт СКУД продолжает работу на последней валидной версии. Для интерактивных запросов к MAX используется более короткий сетевой таймаут, чтобы кнопки и меню не зависали слишком долго при сетевой деградации. Для графиков бот теперь ожидает расширенный диапазон `Графики!A:X`: помимо начала и окончания дня он умеет читать обеденное окно, минуты обеда, норму минут в день и тип вычета обеда. Если явные поля обеда отсутствуют, сервис использует fallback из `Комментарий` в формате `Обед 12:30-14:00`. Для типовых пятидневных графиков зафиксированы нормативы: `ГР003 / Девушки` = `429` минут в день, `ГР004 / Парни` = `480` минут в день. При импорте СКУД поиск сотрудника в справочнике теперь умеет безопасный fallback по нормализованному ФИО: `ё/е`, лишние точки и обрезанное отчество больше не должны уводить строку в ложный fallback-график.
Если runtime поднят без `GOOGLE_SERVICE_ACCOUNT_FILE`, `GOOGLE_SHEETS_SPREADSHEET_ID` или без установленных Google SDK-зависимостей, диагностические экраны (`Обо мне`, `Моя строка`, `Проверить связку`) обязаны явно сообщать, что Google Sheets в этой среде не настроен, а не делать вывод `запись не найдена`.

source ~/skud/scripts/shortcuts.sh

## Прод-режим на Mac mini

Проект рассчитан на два `launchd`-сервиса:

- `com.gooc.attendancebot.backend` — backend на `uvicorn`
- `com.gooc.attendancebot.tunnel` — tunnel в `localhost.run` с автоперерегистрацией webhook; последний живой URL сохраняется в `run/localhostrun.url` и не очищается между переподъёмами

Установка:

```bash
cd ~/skud
chmod +x scripts/*.sh
./scripts/install_launchd.sh
```

Проверка:

```bash
launchctl list | grep attendancebot
tail -f ~/skud/logs/backend.stderr.log
tail -f ~/skud/logs/localhostrun.log
cat ~/skud/run/localhostrun.url
```

Для выкладки кода на прод используй только:

```bash
cd ~/skud
/bin/bash scripts/deploy_prod.sh
```

Этот скрипт синхронизирует только код и не перезаписывает runtime-данные продовой среды: `.env`, `data/`, `logs/`, `run/`.

Backend-лог теперь пишет тайминги по ключевым этапам webhook: общее время обработки, `resolve_role`, чтение dialog state, загрузка Google Sheets и отправка ответов в MAX (`answer_callback`, удаление прошлого сообщения, отправка нового сообщения). Для диагностики отказов MAX HTTP-ответы логируются с кодом и коротким телом ошибки. Cursor последнего сообщения читается и сохраняется пачкой по `chat:*`/`user:*`, чтобы чистый чат не делал лишние SQLite round-trip.

## Прод-режим на Linux через GitHub Actions

Для сервера без входящего SSH из этой среды используется self-hosted GitHub Actions runner. Runner сам забирает задания из GitHub и выполняет локальный деплой на сервере.

На сервере один раз зарегистрируй runner с label `skud-prod`:

```bash
RUNNER_TOKEN=... bash scripts/bootstrap_github_runner_linux.sh
```

После этого каждый push в `main` и ручной `workflow_dispatch` запускает `.github/workflows/deploy.yml`. Деплой выполняет `scripts/deploy_local_linux.sh`: синхронизирует код в `~/skud`, не перезаписывает `.env`, `data/`, `logs/`, `run/`, обновляет `.venv`, ставит user-systemd сервисы и перезапускает:

- `skud-backend.service` — backend на `uvicorn`
- `skud-tunnel.service` — tunnel в `localhost.run` с автоперерегистрацией webhook

Для первого запуска на новом сервере нужно заранее положить runtime-файлы:

- `~/skud/.env`
- `~/skud/data/` при переносе текущей SQLite-базы и загруженных файлов
- Google service account JSON по пути из `.env`

В GitHub Actions деплое `.env` берется из secret `SKUD_ENV`. Для Google Sheets на Linux добавь secret `GOOGLE_SERVICE_ACCOUNT_JSON` с полным содержимым service account JSON и укажи в `SKUD_ENV`:

```env
GOOGLE_SERVICE_ACCOUNT_FILE=/home/localadmin/skud/secure/google-service-account.json
```

Проверка на сервере:

```bash
systemctl --user status skud-backend.service skud-tunnel.service
journalctl --user -u skud-backend.service -u skud-tunnel.service -f
cat ~/skud/run/localhostrun.url
```

### Прямой HTTPS webhook без localhost.run

Если на сервере есть root-доступ, можно убрать задержку tunnel и прокинуть MAX напрямую через nginx. Технический домен по умолчанию — `89-150-35-139.sslip.io`, он указывает прямо на IP сервера:

```bash
cd ~/skud
sudo env SKUD_WEBHOOK_DOMAIN=89-150-35-139.sslip.io bash scripts/install_direct_webhook_nginx.sh
```

Скрипт создает `/etc/nginx/conf.d/skud-webhook.conf`, выпускает Let’s Encrypt сертификат через certbot, проверяет `https://89-150-35-139.sslip.io/api/health`, регистрирует MAX webhook и ставит `SKUD_DISABLE_TUNNEL=true` в `.env`, чтобы `skud-tunnel.service` больше не перерегистрировал webhook обратно на `localhost.run`.

## Регистрация webhook в MAX

После обновления `MAX_BOT_WEBHOOK_URL` и `MAX_BOT_SECRET`:

```bash
cd ~/skud
source .venv/bin/activate
python3 scripts/register_max_webhook.py
```

`register_max_webhook.py` умеет сам взять базовый URL из `run/localhostrun.url`, нормализовать его до `/api/webhooks/max` и обновить `.env`, поэтому после смены tunnel URL не нужен ручной ввод адреса.

Если MAX временно присылает webhook без `X-Max-Bot-Api-Secret`, бот принимает запрос и продолжает обработку, чтобы не терять события. При явном неверном secret webhook по-прежнему отклоняется.

## Локальный кэш справочника

В runtime бот читает роли, руководителей, подразделения, кабинеты и графики из быстрой SQLite-таблицы `employee_directory`. Google Sheets используется как источник синхронизации, а не как обязательный запрос на каждое нажатие.

Ручной запуск синхронизации:

```bash
cd ~/skud
source .venv/bin/activate
python3 scripts/sync_employee_directory.py
```

На Linux `scripts/install_systemd_user_linux.sh` ставит `skud-directory-sync.timer`: он обновляет локальный справочник каждые 6 часов. Если Google service account не настроен, синхронизация мягко пропускается, а бот продолжает работать на последнем локальном кэше.

## Синхронизация связей руководства

После заполнения листа `DOCX_Связи_ШАБЛОН` в Google Sheets можно запустить:

```bash
cd ~/skud
source .venv/bin/activate
python3 docx_leadership_sync.py
```

Скрипт:

- обновит `ФИО_руководителя`, `ID_руководителя`, `Подразделение` и `ID_подразделения` в `Сотрудники`, если они заполнены в шаблоне;
- создаст нормализованный лист `DOCX_Связи_НОРМА` для проверки;
- зафиксирует `Посунько Руслан Юрьевич` как верхний уровень, его прямых замов как уровень ниже, а затем разложит отделы и сотрудников по иерархии из `DOCX_Структура`;
- заполнит `ФИО_руководителя` у сотрудников отдела автоматически по ближайшему руководителю в их ветке, если в шаблоне это поле пустое;
- массово добьет `ФИО_руководителя` и `ID_руководителя` в `Сотрудники` для всех строк, где отдел уже известен, а руководитель пустой;
- нормализует названия подразделений и заново заполнит лист `Подразделения` с их руководителями;
- выставит роль `Руководитель` сотрудникам, которые являются руководителями подразделений;
- оставит замещения как отдельный этап, потому что для них нужны даты действия и причина.

## Полезные URL

- `GET /` — корневой статус
- `GET /api/health` — healthcheck
- `POST /api/webhooks/max` — webhook-заглушка под MAX
- `POST /api/imports/skud/csv?filename=...&created_by_user_id=...` — загрузка CSV выгрузки СКУД

- `GET /docs` — страница с ручной проверкой запросов

## Загрузка файла через MAX

Роли `manager`, `security`, `admin` и `top_manager` могут отправить в бот вложение `csv` или `xlsx`. У начальника отдела загрузка доступна отправкой файла в чат без отдельной кнопки `Отчеты` в главном меню.

Бот:

- заберет файл из сообщения и разберет его; если MAX прислал только краткое вложение без прямого `url`, бот сам подтянет полное сообщение по `message_id`
- сохранит его в `data/uploads/skud/`
- поддерживает сырой `Отчет по проходам`, сводный Excel-отчет `О сотруднике ...` и `Отчет о нарушениях`, где по дням уже даны итоговые колонки `Опоздал`, `Прогулял`, `Начало дня`, `Конец дня`; дробные Excel-значения времени преобразуются в `ЧЧ:ММ`, а если агрегированные минуты пустые или нулевые, статус прихода и ухода вычисляется по фактическому времени и графику сотрудника
- создаст кейсы через импорт СКУД с учетом графика сотрудника из Google Sheets
- сохранит дневной учет проходов: первый вход, последний выход, и статус прихода/ухода по графику
- во вкладке `Трудочасы` подсветит сотрудников с недельным плюсом зеленым, а с просадкой по часам красным; отдельная вкладка `Трудочасы отделы` показывает агрегированную сводку по подразделениям
- если в графике не заполнен `План_минут_в_день`, бот досчитывает план часов из времени начала/окончания и обеда; строки во вкладках отчета сортируются по убыванию отклонения или баланса
- опоздание считается уже с первой минуты сверх планового времени прихода: `+1 минута` и больше попадает в `Опоздавшие`, а не во `Вовремя`
- для сводных файлов `О сотруднике ...` значение `23:59` в поле вечерней отметки трактуется как отсутствие нормального выхода в СКУД: такой день считается прогулом/неявкой, а не переработкой
- управленческий Excel-отчет теперь явно отделяет `Проблемные дни` от обычных статусов: незакрытые выходы, пропущенные входы и дни без проходов не смешиваются с `Вовремя`/`Опоздавшие`
- в сводке отчета totals теперь замыкаются: отдельными строками показываются `Проблемных дней`, `Нет выхода`, `Нет входа`, `Нет проходов` и `Замещения`
- вкладки `Трудочасы` и `Трудочасы отделы` отсортированы по риску для руководителя: сначала проблемные и минусовые дни, а не строки с наибольшим плюсом
- XLSX-листы стали читабельнее для руководителя: добавлены `Тип дня`, freeze первой строки, автофильтр и автоширина колонок
- минутные отклонения в руководительских таблицах теперь показываются со знаком `+/-`, а `Баланс` переименован в более прямой `Итог дня/недели`, чтобы было видно: раньше пришел и позже ушел дают положительное отклонение, а не минус
- в разделах отчетов для руководителя, топ-руководителя, HR и admin появился сценарий `За период`: бот спрашивает дату `с` и дату `по`, после чего формирует отчет именно за выбранные границы; `По отделам` теперь тоже работает через такой выбор периода
- ответит кратким итогом обработки

Обычные ответы в MAX отправляются через `send_message` с fallback-цепочкой: для входящих сообщений сначала используется `chat_id`, затем `user_id`, если первый адрес не сработал. Перед каждым новым видимым ответом на команду бот очищает своё предыдущее сообщение в этом диалоге: убирает кнопки и заменяет текст на невидимый символ, потому что MAX не даёт полноценного bot-side `DELETE` для сообщений. `/start` и `Начать` тоже отправляют свежую карточку через `send_message`, чтобы запуск не терялся в старом отредактированном сообщении. Inline-клики с `message_id` получают неблокирующий `answer_callback` с невидимым notification, чтобы кнопка сразу отпустила нажатие, а готовый экран бот дорисовывает через `edit_message`; callback без `message_id` по-прежнему рендерится через embedded `answer_callback(new_text=...)`. Если MAX отклонит обновление и есть настоящий `chat_id`, бот fallback'ом отправит обычное видимое сообщение. Для push-уведомлений и служебных сообщений применяется обычная доставка. Входящие retry и исходящие ответы дедуплицируются через SQLite `runtime_markers` только по scoped-ключам `chat:*`, `user:*` или `recipient:*`; маркер исходящей отправки фиксируется только после успешного ответа MAX.

Inline-кнопки и другие служебные вложения из callback-сообщений не должны попадать в импорт СКУД: разбор файла запускается только для реальных `message_created` с загрузкой файла.

Роли и справочник сотрудников читаются из Google Sheets с коротким кэшем; если Sheets временно недоступен или упирается в лимит чтения, бот использует последнюю валидную копию вместо падения webhook.

Отчеты по кнопкам `За период`, `Недельный`, `Месячный`, `Квартал` и `По отделам` теперь отправляются в чат как готовые вложения `.xlsx` и `.pdf`, а не только как ссылки на скачивание. Для `За период` и `По отделам` бот сначала спрашивает даты начала и окончания. По запуску бот сразу отвечает сообщением `отчет формируется`, а сама генерация и отправка файлов идут фоном отдельным сообщением. Файлы отправляются независимо: если MAX отклонит PDF, это больше не блокирует доставку Excel. Если дневная таблица учета еще пустая, отчет собирается из уже созданных кейсов, чтобы не приходить пустым. В Excel есть отдельные вкладки `Проблемные дни`, `Опоздавшие`, `Согласованные опоздания`, `Вовремя`, `Раньше`, `Ушли позже`, `Ушли вовремя`, `Ушли раньше`, отдельная вкладка `Трудочасы`, отдельная вкладка `Трудочасы отделы` и общий лист `Случаи`. Внутри отчета есть уже не только дата и статус прихода, но и тип дня, первый вход, последний выход, статусы прихода и ухода, причина сотрудника, кто согласовал и комментарий согласующего. Положительная динамика по трудочасам и переработке подсвечивается зеленым, отрицательная красным. Листы `Трудочасы` и `Трудочасы отделы` теперь читаются блоками: сначала `Просадка`, потом `Нейтрально`, потом `Переработка`.
Для быстрой проверки выгрузки СКУД по вкладкам отделов есть скрипт: `python3 scripts/build_department_skud_report.py /tmp/op1.xlsx -o data/reports/skud_departments_op1.xlsx`; отчет по всем сохраненным кейсам строится через `python3 scripts/build_department_skud_report.py --all-time -o data/reports/skud_departments_all_time.xlsx`. Флаг `--canonical-tabs` создает вкладки по утвержденному списку отделов, а строки с неизвестным подразделением кладет в `Не сопоставлено`; список сотрудников берется из Google Sheets `Сотрудники`, если ключ доступен, иначе из локального справочника. Первым листом идет `К проверке`: приоритет, короткое действие для руководителя, группа проблемы, сотрудник, отдел, дата, приход, уход, проблема, объяснение и статус согласования. Вкладки отделов показывают только конкретные случаи опоздания и раннего ухода с датой, приходом/уходом, планом, минутами отклонения, объяснением и статусом согласования.
Если у руководителя нет подчиненных по `ID_руководителя`, но он сам успешно загрузил выгрузку СКУД, отчет строится по периоду его последней загрузки, а не возвращается пустым.
При заказе нового отчета того же типа для того же пользователя старый отчет и его файл удаляются автоматически.
Кабинет сотрудника теперь разделен на понятные секции: `Опаздываю`, `Опоздания`, `Руководство`. Кнопки `Старт` и `Статистика` из главного меню сотрудника убраны как лишние дубли, а во внутренних экранах добавлена кнопка `Назад`.
Личные экраны сотрудника (`Мои опоздания`, `Объяснить`, `Мои статусы`) сначала ищут случаи по MAX ID пользователя, а если таких записей нет, используют ФИО из справочника сотрудников. Это позволяет показывать импортированные СКУД-кейсы, созданные до заполнения `employee_user_id`.
Сценарий `Забыл карточку СКУД` доступен всем ролям, кроме `Главный руководитель`: пользователь выбирает согласующего, вручную указывает время прихода в формате `ЧЧ:ММ`, после чего создается отдельный кейс и сразу уходит на согласование.
Сценарий `Опаздываю` доступен всем ролям, кроме `Главный руководитель`: пользователь выбирает согласующего, затем дату `Сегодня` или `Завтра`, нажимает `Указать причину`, вводит причину вручную и указывает время `Опаздываю с`. После этого заявка уходит на согласование. У начальника отдела заявки уходят на согласование топ-руководителю.
На текущем этапе опломбирование работает как простое напоминание по сотрудникам с заполненным `Кабинет`: девушкам в 17:10, мужчинам в 17:55. Текст напоминает закрыть дверь и опломбировать кабинет. В сообщении есть кнопка `Спасибо за напоминание`; нажатие показывает короткое подтверждение `Принято, спасибо.` и не пишет строку в `Журнал`.
Напоминания запускаются отдельными командами, которые ставятся в планировщик:

```bash
cd ~/skud
python3 scripts/send_office_seal_reminders.py female  # 17:10
python3 scripts/send_office_seal_reminders.py male    # 17:55
./scripts/install_office_seal_summary_launchd.sh      # launchd-задачи для двух напоминаний
```
На Linux эти напоминания ставятся как user-systemd timer'ы при `scripts/install_systemd_user_linux.sh` /
`scripts/deploy_local_linux.sh`: `skud-office-seal-reminder-female.timer` и
`skud-office-seal-reminder-male.timer`.
Скрипты напоминаний и сводок берут короткий leader-lease в `runtime_markers`, поэтому параллельные scheduler-процессы не рассылают одну и ту же пачку повторно.
Если сотрудник выходит раньше запланированного срока, он может открыть свой случай отсутствия и нажать `Выйду раньше`, после чего бот запросит новую дату окончания, обновит период и отправит руководителю повторное согласование.
Push-уведомления руководителю по причинам и уведомлениям больше не содержат мгновенную кнопку `Согласовать`: в них остается компактная кнопка `Открыть`, а подтверждение или отклонение выполняется уже в карточке согласования.
При отказе по заявкам `Опаздываю` и `Забыл карточку СКУД` согласующий сначала вводит причину отказа; она сохраняется в согласовании и отправляется заявителю.
После согласования или отклонения заявки бот отправляет заявителю отдельное уведомление с решением и ФИО согласующего; если в старом кейсе не сохранен MAX ID заявителя, бот ищет его в справочнике по ФИО, а при отказе MAX принять отправку по `user_id` пробует сохраненный `chat_id` диалога.
При следующей загрузке СКУД импорт пытается найти такую заявку `Опаздываю` по сотруднику и дате. Если находит, он обновляет этот кейс фактическим временем прихода из СКУД и не создает дубль.
Inline-кнопки в боте теперь раскладываются адаптивно: длинные подписи автоматически переносятся на отдельные строки, чтобы причины и отчетные действия помещались на экран и читались без обрезания.

## Быстрый тест сценария замещения

1. Отправить стартовое сообщение:

```json
{
  "event_type": "message",
  "text": "/start",
  "user": {
    "id": "mgr_001",
    "username": "manager.test",
    "full_name": "Тестовый Руководитель"
  },
  "chat": {
    "id": "private_001",
    "type": "private"
  }
}
```

2. Затем последовательно отправлять в тот же webhook.

Для кнопок лучше отправлять `action`, а для свободного ввода обычный `text`.

- `action=menu.substitutions`, `text=Замещения`
- `action=substitution.create`, `text=Назначить замещение`
- `Петров Петр Сергеевич`
- `Волков Игорь Павлович`
- `action=Отпуск`, `text=Отпуск`
- `2026-07-01`
- `2026-07-14`
- `action=substitution.department:Отдел продаж`, `text=Отдел продаж`
- `action=substitution.departments.done`, `text=Готово`
- `action=common.confirm`, `text=Подтвердить`

## Быстрый тест сценария причины опоздания

1. Отправить `/start`, затем открыть `Мои опоздания`.
2. Открыть случай со статусом `Ожидает ответа сотрудника`.
3. Нажать `Выбрать руководителя`.
4. Выбрать руководителя из списка.
5. Нажать причину опоздания.

Для кнопок сценария причины:

- `action=employee.reason.start:101`, `text=Выбрать руководителя`
- `action=employee.manager:101:mgr-alt`, `text=Смирнов Сергей Олегович`
- `action=employee.reason:101:personal_reason`, `text=Личная причина`
