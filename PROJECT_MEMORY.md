## Версии и стек
- Python backend на `FastAPI`; точка приложения: `app/main.py`.
- Версия приложения в `FastAPI`: `0.1.0`.
- Основные зависимости из `requirements.txt`: `fastapi`, `uvicorn`, `python-dotenv`, `sqlalchemy`, `openpyxl`, `google-api-python-client`, `google-auth`.
- MAX API по умолчанию: `MAX_API_VERSION=1.2.5`, base URL `https://platform-api.max.ru/`, интерактивный timeout `MAX_API_TIMEOUT_SECONDS=3`.
- База по умолчанию: SQLite `sqlite:///./data/attendance_bot.db`.
- Google Sheets диапазоны по умолчанию: `Сотрудники!A:R`, `Графики!A:X`.

## Точки входа

- `app/api/routes/max_webhook.py` принимает webhook MAX.
- `app/bot/router.py`, `app/bot/actions.py`, `app/bot/buttons.py`, `app/bot/menus.py` отвечают за диалоги, действия и кнопки бота.
- `create_google_sheet.py` создает и обновляет структуру Google Sheets, включая загрузку справочников.
- `docx_leadership_sync.py` синхронизирует структуру руководства из Google Sheets.
- `scripts/register_max_webhook.py` регистрирует webhook MAX и умеет брать public URL из `run/localhostrun.url`.
- `scripts/install_direct_webhook_nginx.sh` и `scripts/install_hike89reg_direct_webhook.sh` настраивают прямой HTTPS webhook через nginx/certbot для домена `SKUD_WEBHOOK_DOMAIN` и после успешной проверки ставят `SKUD_DISABLE_TUNNEL=true`; для prod `BOTSGSN` использовать `install_hike89reg_direct_webhook.sh`, он пишет `/etc/nginx/conf.d/skud-webhook.conf`.
- `scripts/deploy_prod.sh` используется для выкладки на прод и не должен перезаписывать `.env`, `data/`, `logs/`, `run/`.
- Linux-прод через GitHub Actions: `.github/workflows/deploy.yml` запускается на self-hosted runner с label `skud-prod`; `scripts/deploy_local_linux.sh` деплоит код в `~/skud`, сохраняет `.env`, `data/`, `logs/`, `run/`, обновляет `.venv` и перезапускает user-systemd сервисы `skud-backend.service` и `skud-tunnel.service`.
- `scripts/bootstrap_github_runner_linux.sh` регистрирует self-hosted runner для репозитория `Gooc-art/max-attendance-bot`; для первичной настройки нужен одноразовый `RUNNER_TOKEN`.

## Устойчивые правила кода
- Роли пользователю показывать по-русски; внутренние коды ролей оставлять техническими. Внутренняя роль `manager` для пользователя отображается как `Начальник отдела`, не как `Руководитель`.
- В Google Sheets прямые заместители главного руководителя записываются в колонке `Роль` как `Зам_руководителя`, начальники отделов — как `Начальник отдела`; при чтении обе метки нормализуются во внутреннюю роль `manager`.
- Для статистики входов в бот использовать агрегированный учет по `user_id`: первый старт, последний старт, последнее взаимодействие.
- Для отсутствий в MAX использовать период `с`/`по`; досрочный выход означает сокращение даты окончания существующего случая.
- Только активные согласованные замещения должны заменять руководителя в сценариях выбора согласующего, включая `Опаздываю`: сотрудник видит замещающего вместо отсутствующего руководителя на период замещения, а снятые/отмененные/истекшие замещения больше не влияют на выбор.
- Для дат замещений принимать `YYYY-MM-DD` и `YYYY.MM.DD`; новые записи нормализовать в `YYYY-MM-DD`, а поиск активных замещений должен учитывать старые записи с точками.
- В сценарии `Опаздываю` после выбора руководителя нужно выбрать дату `Сегодня` или `Завтра`, нажать `Указать причину`, вручную ввести причину и время `Опаздываю с`; `Буду отсутствовать`, `Согласовано` и `Личная причина` в этом сценарии не показывать.
- Для загрузки справочников в Google Sheets использовать `create_google_sheet.py` и держать его в синхроне с `staff_catalog.json` и `staff_bindings.json`.
- При runtime без Google Sheets-настроек диагностические экраны должны явно сообщать, что Google Sheets не настроен, а не показывать `запись не найдена`.
- После согласования или отказа бот уведомляет заявителя; если в кейсе нет `employee_user_id`, получатель ищется в справочнике по ФИО, а если MAX отклоняет отправку по `user_id`, используется сохраненный `chat_id` диалога.
- Для заявок `Опаздываю` и `Забыл карточку СКУД` отказ согласующего должен проходить через ввод причины отказа; текст сохраняется в `approval.comment` и показывается заявителю.
- `MaxWebhookRouter` и `RoleResolver` используют один экземпляр `GoogleSheetsDirectoryService`, чтобы роль и сценарии бота делили один in-memory кэш справочника в процессе.
- Runtime-источник для ролей, руководителей, подразделений, кабинетов и графиков — локальная SQLite-таблица `employee_directory`; Google Sheets синхронизируется в нее скриптом `scripts/sync_employee_directory.py` и user-systemd timer `skud-directory-sync.timer` раз в 6 часов. Если Google недоступен, бот работает на последнем локальном кэше.
- При старте сценариев `Опаздываю` и `Забыл карточку СКУД`, если строка сотрудника не найдена в быстром кэше справочника, делать один `refresh=True` перед ошибкой о привязке ID; для найденных строк оставлять быстрый cached path.
- Для правила чистого чата бот хранит последний `message_id` по `chat_id` и `user_id` и перед новым видимым ответом сначала пробует удалить прошлое сообщение через MAX `DELETE /messages`; если MAX отказывает, fallback — soft-clear через edit в невидимый текст. Если callback приходит без реального `chat_id`, не отправлять новый `send_message` по старому сохраненному чату: MAX может вернуть 403; использовать embedded `answer_callback`.
- Cursor чистого чата читать/писать пачкой для ключей `chat:*` и `user:*`, чтобы не плодить SQLite-сессии на каждый видимый ответ.
- Для `message_callback` без верхнего `chat_id` не считать вложенный `message.recipient.chat_id` пригодным для нового `send_message`: на практике MAX возвращает `403`. Такой callback надо рендерить через embedded `answer_callback`.
- Inline-клики с `message.body.mid` подтверждать неблокирующим `answer_callback` с невидимым notification, затем обновлять карточку через `edit_message`; callback без `mid` рендерить через embedded `answer_callback(new_text=...)`. Если MAX отклонит обновление и есть настоящий `chat_id`, fallback — обычный visible send. После обновления callback-карточки сохранять `message.body.mid` как актуальный cursor, иначе следующий обычный ответ будет чистить устаревшее сообщение.
- В продовом `app/api/routes/max_webhook.py` callback-ответы MAX отправляются фоном через `MaxWebhookRouter(async_callback_outbound=True)`: webhook быстро возвращает `ok`, а `_send_outbound_sync` делает фактический `answer_callback`/`edit_message` в daemon-thread. Прямой `MaxWebhookRouter()` по умолчанию остается синхронным для тестов и ручной диагностики.
- Для защиты от retry/echo/параллельных процессов используется SQLite-таблица `runtime_markers`: входящие MAX события и исходящие ответы дедуплицируются только по scoped `chat:*`, `user:*` или `recipient:*` ключам, без глобального fallback. Outgoing marker резервируется перед MAX API и переводится в `done` только после успешной отправки; при ошибке marker удаляется для безопасного retry.
- Навигационные кнопки кабинета, включая `Мои опоздания`, должны перебивать активные сценарии диалога: сначала сбрасывать `dialog_state`, затем открывать нужный раздел, иначе пользователь может застрять в flow и кнопка будет казаться нерабочей.
- Видимое главное меню держать чистым: не показывать `Старт` у основных ролей; у сотрудника `Мой кабинет` находится в разделе `Руководство`; у администратора диагностика `Админ-панель` и `Права доступа` находится внутри `Личное`; во вложенных разделах не дублировать одинаковый возврат кнопками `Назад` и `Главное меню`.
- Личные экраны сотрудника (`Мои опоздания`, `Объяснить`, `Мои статусы`, `Статистика`) ищут кейсы по `employee_user_id`, а если прямых записей нет, добирают их по ФИО из Google Sheets/локального справочника, чтобы старые импортные кейсы без MAX ID были видны сотруднику.
- Экран `Обо мне` сначала читает локальный `employee_directory` и не дергает Google Sheets, если локальная запись найдена; Google используется только как fallback, чтобы простой личный экран не висел на сетевой загрузке справочника.
- `MaxWebhookRouter` кэширует записи справочника и по `employee_user_id`, и по ФИО сотрудника на 5 минут; это нужно для быстрых повторных inline-кликов и при этом сохраняет проверку расхождений между ФИО руководителя и `manager_user_id`.
- В flow `Опаздываю` и `Забыл карточку СКУД` варианты руководителей сохраняются в `dialog_state.manager_options`, чтобы следующий клик выбора руководителя не резолвил имя через справочник повторно; уведомление руководителю после финального ввода отправляется фоном и не задерживает ответ сотруднику.
- При `SKUD_DISABLE_TUNNEL=true` user-systemd tunnel service должен завершаться без рестарт-цикла (`Restart=on-failure`), а `deploy_local_linux.sh` должен останавливать `skud-tunnel.service` и не ждать stale `run/localhostrun.url`.
- На `BOTSGSN` nginx локально отдает `/api/health` и ACME challenge для `89-150-35-139.sslip.io`, но публичные HTTP/HTTPS запросы к `89.150.35.139` проходят через внешний frontend/Azure Application Gateway и не попадают в этот nginx; direct webhook на этом домене нельзя включить только sudo-скриптом на `BOTSGSN`, пока внешний маршрут/шлюз не прокинут `/api/*` или 80/443 на этот сервер.
- Опломбирование кабинетов сейчас упрощено до напоминаний: сотрудникам с заполненным `Кабинет` отправлять reminder девушкам в 17:10, мужчинам в 17:55; текст напоминает закрыть дверь и опломбировать кабинет; кнопка `Спасибо за напоминание` отвечает быстрым callback-подтверждением и не пишет строку в `Журнал`.
- На Linux напоминания опломбирования ставятся user-systemd таймерами `skud-office-seal-reminder-female.timer` и `skud-office-seal-reminder-male.timer` через `scripts/install_systemd_user_linux.sh`.
- Scheduler-скрипты напоминаний/сводок опломбирования берут daily leader-lease в `runtime_markers`, чтобы параллельные процессы не отправляли одну пачку повторно.
- Excel-выгрузка `scripts/build_department_skud_report.py` по отделам первым листом показывает `К проверке`: приоритет, короткое действие для руководителя, группа проблемы, сотрудник, отдел, дата, приход/уход, проблема, объяснение и согласование; вкладки отделов показывают только конкретные случаи опоздания и раннего ухода.
